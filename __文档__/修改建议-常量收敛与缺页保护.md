# 修改建议：常量收敛 + 缺页保护

> 依据 2026-08-30 代码评审第 4、5 点展开。
> 本文档只写**方案与预期效果**，不落地代码；实施时按"落地步骤"分层推进并回归 CLI 与 Web 两条链路。

---

## 一、第 4 点：关键常量散落多处，极易漂移

### 1.1 现状问题盘点

默认参数与逻辑重复分散在至少 7 处，改一处忘一处就会造成 CLI 与 Web 行为不一致：

| 常量 / 逻辑 | 出现位置 |
|---|---|
| 默认放大倍数 `4` | run.py、server/main.py `JobRequest`、jobs.py 调 `process_one` 兜底、appControl.js、README |
| 默认目标宽度 `4320` | run.py、server/main.py、jobs.py、appControl.js、README |
| 默认模型 `realesrgan-x4plus` | run.py、server/main.py、jobs.py、appControl.js、Sidebar.vue、README |
| 模型白名单（2 个模型） | appControl.js 与 Sidebar.vue 各写一份 |
| 日志文件白名单 extract/upscale/rebuild | server/logs.py、appState.js、LogPanel.vue |
| 成品路径推导 `output/<书名>_clear.pdf` | core/pipeline.process_one 与 server/files._out_path_for（重复） |
| work 目录推导 `work/<书名>/` | core/pipeline 与 server/logs._log_path（重复） |
| GPU 默认 `"0"` | run.py、jobs.py |

前端两个 `.js` 文件都从各自硬编码的模型/日志清单读取；后端 `files`/`logs` 各自复刻 pipeline 的路径算法——这类"影子实现"一旦一方改动另一方就会悄悄漂移。

### 1.2 修改方案

**后端（先行落地）：**

1. 新建 `core/config.py`（或在现有 `core/paths.py` 旁追加 `core/defaults.py`），集中声明：
   - `DEFAULT_SCALE = 4`、`DEFAULT_TARGET_WIDTH = 4320`、`DEFAULT_MODEL = "realesrgan-x4plus"`、`DEFAULT_GPU = "0"`；
   - `MODELS`（模型白名单，读取 `bin/realesrgan/models/` 下 `.param` 文件名推导，避免手工维护两份清单）；
   - `STAGE_WEIGHTS = {"extract": 0.20, "upscale": 0.70, "rebuild": 0.10}`、`STAGE_BASE`、`STAGE_TAG`（从 jobs.py 上移）。
2. 在 `core/paths.py` 增加两个共享函数，替换影子实现：
   - `out_path_for(pdf)` → `output/<书名>_clear.pdf`；
   - `work_dir_for(pdf)` → `work/<书名>/`。
3. `core/pipeline.py`、`server/files.py`、`server/logs.py`、`server/jobs.py` 全部改为从上述常量/函数取值，删除各自的本地推导。
4. `server/main.py` 的 `JobRequest`：
   - `model` 用白名单校验（Pydantic `Literal[*MODELS]` 或自定义 validator），非法值直接 422；
   - `extract_workers` 上限收敛到 `os.cpu_count()`；
   - `gpu_ids` 校验必须是自检枚举出的编号或空串。

**前端（随后落地）：**

5. 后端 `/api/state` 增发 `models` 白名单（`gpus`/`cpu_count` 已有）；
6. 删除 appControl.js 与 Sidebar.vue 里的硬编码 `MODELS`，改为从 state 读取；
7. 新建 `ui/src/constants.js` 承载 `LOG_FILES`，appState.js 与 LogPanel.vue 统一引用（或由后端下发）。

**文档：** README / 文件结构.md 同步默认值描述。

### 1.3 预期效果

- 单一事实源：改一处默认值/新增模型，CLI 与 Web 全链路生效，消除漂移回归；
- 非法参数（未知模型、超大线程数、非法 GPU）在服务端即被拒绝，不再落到引擎侧报晦涩错误；
- 新增模型时不再需要改 4 个文件；
- 路径算法唯一，`files.inspect` 预告的"成品已存在"与 pipeline 实际输出永远一致。

### 1.4 影响面与风险

- 涉及 core / server / ui 三端，建议按"后端常量+函数 → 服务端校验 → 前端取用"分层落地，每层跑一遍 CLI 单文件 + Web 全流程回归；
- 行为兼容性高，属于重构而非功能变更；唯一可见变化是 API 对非法参数从"透传报引擎错"变为"提前 4xx"。

## 二、第 5 点：缺页不阻断，可能静默产出"少页成品"

### 2.1 现状问题

- `core/pipeline.py::upscale`：超分输出页数 `up_count != total` 时仅打一行 `WARN`，之后照常进入重建；
- `scripts/rebuild_pdf.py`：用 `glob` 现有图重建，`*.png` 少几张它就用几张，退出码仍为 0；
- 结果：某几页提取/超分失败时，最终 PDF 会**静默缺页**，用户拿到手才发现，且无任何终态提示。

（注：extract 阶段已有 `ok != n` 硬校验，缺页风险主要来自超分与重建两段。）

### 2.2 修改方案

1. **超分阶段缺页 → 硬失败**
   - `core/pipeline.py::upscale`：把"输出页数 ≠ 源页数"从 WARN 改为返回错误（视为失败，`on_done(False)`）；
   - 保留现有兼容分支：`全部页已生成但退出码非 0` 仍按成功处理（应对杀软/驱动/沙箱环境），仅对**页数不足**严格化。

2. **重建阶段页数校验 → 硬失败**
   - `scripts/rebuild_pdf.py` 新增 `--expect-pages N` 参数（N = 参考 PDF 页数）；
   - 末尾 `len(files) != N` 或写出的页数 != N 时，非零退出并打印缺页明细（缺失的页码）；
   - `core/pipeline.py` 在调用 rebuild 时传入该参数（`pages` 探测失败时降级为不校验并 WARN，避免误杀）。

3. **Web 端终态透出**
   - `server/jobs.py`：失败时的 `error` 信息携带阶段与缺页情况（如"超分缺 3 页：page_0005/0011/0098"）；
   - 前端 WorkPage 失败态直接展示该信息，LogPanel 对应阶段 tab 高亮相关行。

4. **（可选）重试提示**
   - 缺页失败后前端提示"重跑会自动清理残留中间图"，引导用户重试（`process_one` 已有清理逻辑，无需新代码）。

### 2.3 预期效果

- 任何阶段缺页都会让任务以 `error` 终止，不再产出"看起来成功但缺页"的成品；
- 失败信息可精确定位到阶段与缺失页码，用户能判断是重试还是排查输入文件；
- 页数校验基于文件系统计数，与现有进度机制同一依据，不引入新的状态源。

### 2.4 影响面与风险

- 改变 `process_one` 的失败语义：原"少页也出成品"变为"少页即失败"，需同步回归 CLI 退出码与 Web 状态展示；
- 需保证 `count_png`/`count_tmp_jpg` 依据可靠（文件系统 listdir，可靠）；多任务并发已由 jobs.py 单任务锁保证，不会串扰计数；
- 兼容性分支（全页生成但退出码非 0）必须保留，否则杀软环境会出现误杀。

---

## 三、落地建议顺序

1. 后端：`core/config.py` + `core/paths.py` 共享函数，替换 `files`/`logs`/`pipeline` 影子实现；
2. 后端：`JobRequest` 白名单校验 + `upscale` 缺页硬失败 + `rebuild --expect-pages`；
3. 前端：state 下发 `models`，删除硬编码，抽 `constants.js`；
4. 回归：CLI 单文件 / 批量 / 取消 / Web 全流程，重点验证"造一个缺页输入"能稳定失败并给出可读信息。
